# CME Internship & Training Portal — Django Edition

A Python/Django rebuild of the CME Internship & Training Portal. It does **not** use Node.js, React, npm, Supabase, or a hosted database. The default database is local SQLite; the UI uses Django templates, HTML, and CSS.

## Access policy — no public registration
- There is **no public sign-up or self-registration page or route**. `/register/` and `/signup/` are not configured.
- Only an authorised CME administrator creates accounts in the Django admin console and assigns each account a role/profile.
- Interns and team members sign in using credentials issued directly by CME. Passwords should be shared privately and changed after first sign-in.

## Included modules
- Premium responsive dark navy / electric blue / violet CME portal landing page and member sign-in
- Role-based workspace: Administrator, Founder, Intern Head, HR/Evaluator, Intern
- Internship & training program catalogue with admin-managed descriptions, eligibility, duration, dates, and status
- Task management with role-based permissions, intern submissions, review feedback, and controlled point awards
- Attendance records
- Announcements with audience targeting
- Certificate records and public verification page for issued certificates
- Django admin console for managing users, profiles, tasks, submissions, attendance, announcements and certificates
- Basic automated tests

## Windows setup (PowerShell)
```powershell
cd CME_Training_Internship_Django
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```
Open `http://127.0.0.1:8000/` for the portal, `/programs/` for internship programs, and `http://127.0.0.1:8000/admin/` for administration.

## First-time setup
1. Create the initial administrator using `python manage.py createsuperuser`. This is an administrative setup step, not a public registration feature.
2. Sign in at `/admin/`.
3. Create intern/HR users under **Authentication and Authorization → Users**.
4. Create a **Profile** for each user and select the appropriate role. Intern IDs are generated when an Intern profile is saved. If an HR/evaluator account should use the Django admin console, enable **Staff status** on that user.
5. Create Founder and Intern Head accounts by creating a user and assigning the matching Profile role. These roles and the Administrator can create/edit tasks, set maximum task points, review intern submissions, and award points. HR/Evaluator accounts are view-only for published tasks. Interns can view their assigned/published tasks and submit work only; they cannot create tasks, change point values, review submissions, or award points. The Django admin console is restricted to superusers.
6. Interns sign in at `/login/` with the username/email and password created by the administrator. There is still no public self-registration route.

## Certificate verification
Create a Certificate record in Django admin and mark **Is issued** only after approval. Open `/verify/<certificate-code>/` to show its verification page. Codes are generated by the model and are not government-issued credentials.

## Security and production notes
- Public self-registration is disabled; account creation is admin-managed.
- Change `DJANGO_SECRET_KEY`, set `DJANGO_DEBUG=False`, and configure `DJANGO_ALLOWED_HOSTS` before deployment.
- SQLite is suitable for local development and small pilots. A production deployment should use a managed database, HTTPS, backups, and a configured email provider if email notifications/OTP are required.
- This starter includes no fake user records or demo credentials. Charts and dashboard counts use actual database records.
- Email OTP, file uploads, payment processing, PDF certificate rendering and automatic certificate eligibility are not implemented in this build; certificate records and code verification are implemented.

## Program and batch isolation (added)

The portal now supports a program → batch → participant structure:
- Create an internship program in **Admin console → Internship programs**.
- Create batches in **Admin console → Internship batches**. Batch codes must be unique within a program.
- Open each intern's **Profile** and assign both `Assigned program` and `Assigned batch`. The selected batch must belong to the selected program.
- When creating tasks, choose a program and optionally a batch. Program-level tasks (no batch selected) are visible to assigned members of that program; batch tasks are visible only to members assigned to that exact batch.
- Scope announcements, attendance records, and certificates to the correct program/batch in the admin console.
- Founder / Co-Founder / Administrator can view the complete program catalogue. Interns see only their assigned program and batch. Other staff work within their assigned program/batch.
- If an intern is not assigned yet, their program/task workspace is empty and asks them to contact an administrator; it does not expose other cohorts.

### Data preservation
This source ZIP intentionally does **not** include `db.sqlite3`; your current database must stay in its existing location and must not be replaced with a blank database. Migration `0006_program_batches.py` is additive: it creates the batch table and adds nullable program/batch links. It does not delete existing users, programs, tasks, submissions, attendance, announcements, or certificates. Existing historical records remain in the database; because legacy records have no batch association, they are not automatically shown inside a specific intern's scoped workspace. An authorized administrator can associate relevant historical records with the correct program/batch. **Back up the existing `db.sqlite3` before deploying and run `python manage.py migrate` against that same database. Do not replace the database file with a blank one.**

## Vercel deployment (static assets + database)

1. Import the repository/project into Vercel and use the repository root that contains `manage.py`, `vercel.json`, and `build_files.sh`.
2. The included `vercel.json` routes requests to the Django WSGI app. `build_files.sh` runs `collectstatic`; WhiteNoise serves collected CSS, images, and other static assets from `/static/`.
3. Set these Vercel environment variables for Preview and Production as appropriate:
   - `DJANGO_SECRET_KEY`: a long, random secret generated privately.
   - `DJANGO_DEBUG`: `False`.
   - `DJANGO_ALLOWED_HOSTS`: `.vercel.app` plus your custom domain if any.
   - `DJANGO_CSRF_TRUSTED_ORIGINS`: comma-separated full origins, e.g. `https://your-project.vercel.app`.
   - `DATABASE_URL`: a managed PostgreSQL connection string. Keep it secret; never commit it.
   - `CME_FOUNDER_PASSWORD`: set privately only if you want the deployment's optional `create_founder` command to set the founder account password. If absent, that command safely skips.
4. Run `python manage.py migrate` against the configured production database after backing up/importing any data that must be retained. Vercel's filesystem is ephemeral: do not rely on SQLite for durable production data. The project ZIP intentionally excludes `db.sqlite3` to avoid overwriting your existing local database.
5. Deploy a Preview first. Verify `/static/portal/styles.css` returns CSS (not HTML), `/static/portal/cme-logo-mark.png` returns the image, and sign-in/dashboard/program/task permissions work before promoting to Production.

### Database safety

Local development continues to use `db.sqlite3` unless `DATABASE_URL` is set. Never delete or replace your current SQLite file. For an existing production deployment, configure the same managed database that contains the records you intend to preserve before running migrations; a fresh empty database will not contain your existing accounts or records.
